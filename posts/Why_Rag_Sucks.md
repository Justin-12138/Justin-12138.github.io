# Why RAG Sucks：当“相关”不等于“可回答”

最近一直在做文档问答。最初的想法非常朴素：把 PDF 切成块，算 embedding，用户提问时召回最相似的几块，再交给 LLM 回答。按这个思路，RAG 看起来只是一个“向量数据库 + Prompt”的工程问题。

真正把系统做起来之后，我越来越觉得这句话是对的：**大部分 RAG 确实很烂。**

但问题不在 RAG 这个词，也不在 embedding 模型本身。问题在于，我们经常把“检索”误解成“找几段看起来相似的文本”，然后期待 LLM 自动完成剩下的信息筛选、证据拼接、口径判断和事实核验。

这中间少了太多东西。

我最近主要在两个项目里踩坑：

- `ragdetail`：直接对 PDF 的页面做 embedding，比较 dense、BM25 + dense hybrid、hybrid + rerank 三种检索方式；
- `optpgi`：先把 PDF 通过 VLM 转成 Markdown，再按标题层级构建文档树，基于页面摘要、文档元数据和多轮上下文做检索回答。

样本是一组 AIA 2022–2025 年年度业绩报告。每篇大约 76–99 页，单独看并不算大。但就是在这种规模下，一个朴素 RAG 该暴露的问题，几乎都暴露了。

---

## 1. 第一个幻觉：把文本切块，等于理解文档

最朴素的 RAG 是固定长度切块，例如每 500 字一块，重叠 50 字。这样做很工程化，也很容易实现，但它隐含了一个很强的假设：

> 只要窗口足够大，语义边界就不重要。

对于连续叙述的博客文章，这个假设偶尔成立。对于财报、研报、产品手册和带大量表格的 PDF，基本不成立。

一页财报可能同时包含：

- 标题和期间；
- 一张汇总表；
- 两个分地区图表；
- 脚注和统计口径；
- “同比增长”“固定汇率”“IFRS 17”之类的限定条件。

固定切块很容易把表头切到上一块，把脚注切到下一块。模型召回一行数字，却没有召回这一行的期间和口径；或者召回了图表结论，却没有召回定义它的上下文。

即使改成“一页一块”，事情也只是好一点。页是 PDF 的物理边界，不一定是语义边界。一个跨页表格、一段接续说明，或者一个从总览页展开到明细页的问题，仍然需要跨多个页面组织证据。

在 `ragdetail` 里，我先做了页面级索引：每页 Markdown 对应一个 embedding，同时保留 BM25、混合排序和 rerank 的对比路径。页面粒度比随机切块自然得多，至少“第 46 页”这种引用是可以验证的。

但这只解决了召回单位的问题，没有解决文档结构的问题。

于是 `optpgi` 走了另一条路：

```text
PDF
  → 页面图片
  → VLM 逐页转 Markdown
  → 按标题构造树
  → 页面摘要 + 文档描述 + 关键词
  → 检索与回答
```

在这个样本里，四篇文档的顶层页面单元分别是 78、85、76 和 99 个。每个节点不只有 `index`，还保留 `title`、`summary`、`prefix_summary` 和正文关系。

这带来的变化不是“树形 UI 更好看”，而是检索时终于有了层级信号：

- 文档级元数据负责限定范围；
- 章节标题负责表达主题；
- 页面摘要负责表达这一页具体讲了什么；
- 正文只在确认相关后按需加载。

文档结构本身就是一种索引。丢掉它，再让 embedding 从一堆碎片里猜回来，成本高且不稳定。

## 2. “相似”与“能回答”是两件不同的事

向量检索最容易被误用的地方，是把相似度当成了答案质量。

假设用户问的是“香港市场在 2022 年的 OPAT 占比是多少”。一个页面如果反复出现 Hong Kong、OPAT 和 2022，它当然会获得很高的相似度。但它可能只是在讲香港业务增长，并没有那张分地区占比表。

反过来，真正包含答案的页面可能非常短，甚至主要是一张表。文本语义并不丰富，但它恰好有用户需要的数字。

这就是第一类错位：

> **Topical relevance ≠ evidential sufficiency.**

“这段文本和问题有关”不等于“这段文本足以回答问题”。

纯 dense retrieval 擅长处理同义改写和自然语言描述；BM25 更擅长精确术语、指标缩写和数字附近的匹配；rerank 则能在候选集已经存在的前提下，更细致地判断问题与候选之间的支持关系。

三者不是互相替代的关系：

```text
Query
  ├─ BM25 召回：保住精确术语、缩写、年份、数字
  ├─ Embedding 召回：保住语义改写和表达差异
  └─ 候选融合
       → rerank / LLM 选页
       → 只加载被选中的正文
```

`ragdetail` 的价值，就是把 dense、hybrid 和 hybrid + rerank 放在同一条查询入口下，能直接看出问题出在哪一层：

- dense 没召回，说明表示或粒度有问题；
- dense 召回了但排得太后，说明排序有问题；
- 候选里有正确页，但最终没进上下文，说明预算或选择策略有问题；
- 正确页进了上下文，答案仍错，才轮到回答模型和 Prompt。

如果不拆开这些层次，最后只会得到一句没有信息量的结论：“RAG 效果不好。”

## 3. 最致命的错误，往往发生在召回之前

`optpgi` 里让我印象最深的一个 case，不是 embedding 排错了，也不是 rerank 分数不好，而是整篇文档在第一层就被丢掉了。

问题是：

> 为什么泰国金融顾问计划有助于 AIA 提升代理渠道质量？

人工检查后，答案需要两份证据：

- 2023 年报告第 46 页：FA 人数、生产力、代理渠道表现；
- 2025 年报告第 46 页：FA 项目机制、留存率、扩员和职业发展路径。

但当时的链路是：

```text
query
  → LLM 选择文档
  → 对每个被选文档做页级选择
  → 取页面正文
  → 回答
```

文档选择 Prompt 里有一条规则：问题没有明确时间信息时，优先最新文档。模型严格照做了，只选了 2025。于是 2023 的第 46 页从未进入候选池。

后面的选页模型再准确，也不可能召回一个根本没被传进去的文档。

这是级联检索里最危险的事情：

> **第一层用粗粒度信息做了硬剪枝，第二层再精确也无法恢复。**

文档描述通常只有一两段，无法表达“这个主题在某一年报告里出现过”。让一个文档级 LLM 调用决定整篇文档的生死，本质上是在错误的信息粒度上做不可逆决策。

修正方向并不是“换一个更大的 embedding 模型”，而是重做检索策略：

1. 用户明确写了年份，就做确定性过滤，不交给模型猜；
2. 用户明确说“最新”，才只取最新；
3. 用户没有写时间，先判断问题类型；
4. 数值题可以优先最新报告，因为通常包含上一期比较数字；
5. 定性、解释、策略类问题不能默认只取最新，应该允许跨年召回；
6. 文档层只负责范围和宽松召回，精确排序放到页级。

这背后是一个简单原则：

> **越粗的层级，越不应该做越硬的判断。**

文档可以过滤范围，页可以精确排序，正文可以交给回答模型。把职责放反，就会得到一个看似聪明、实际上不断丢证据的流水线。

## 4. 把整棵文档树塞进 Context，也是一种 RAG 反模式

早期方案还有一个非常典型的问题：以为页面摘要足够短，于是每一轮都把整本文档的页面列表交给 LLM 选页。

项目笔记里统计过 `remove_all()` 之后的 page list：

| 文档 | 页面数 | page list 约 tokens |
| --- | ---: | ---: |
| 2022 | 78 | 22.5k |
| 2023 | 85 | 26.6k |
| 2024 | 76 | 23.8k |
| 2025 | 99 | 29.1k |

如果一次选四个文档，只做页选择就需要接近 100k tokens。更糟的是，摘要并不总是真的摘要。部分短节点直接把原文当成了 summary，免责声明页甚至能产生几千字符的“索引项”。

这里的问题不是上下文窗口是否放得下，而是：

- 每一轮都在为无关页面付 token；
- 候选越长，模型越容易挑错；
- 多轮对话后，成本和延迟会迅速失控；
- 索引和正文混在一起，无法只加载真正需要的证据。

后来的改造把摘要重新定义成“检索信号”，而不是“内容压缩后的另一个全文版本”：

- 叶子页面只描述主题、关键指标、实体和期间；
- 父节点根据子节点摘要自底向上生成；
- 单次摘要限制在 1–2 句话，并设置输出 token 和字符上限；
- 同时产出紧凑索引 `<doc>.index.json` 与按需加载的正文 `<doc>.pages.json`；
- 文档树不再承担“把整篇报告塞进 Prompt”的职责。

这个改造并没有神奇地消灭 RAG。它只是让每个 token 都有了明确用途：索引负责筛选，正文负责证据。

## 5. 多轮对话不是把历史记录拼在 Prompt 后面

单轮检索已经足够复杂，多轮对话会把问题再放大一次。

用户说“那 2023 年呢？”“把刚才那个表做成对比”“这个说法在哪一页？”，如果直接拿原问题去检索，代词和省略信息会全部丢失。如果为了保留指代，把完整历史都塞进上下文，又会引入旧数字、旧结论和无关页面。

`optpgi` 后来把记忆拆成三层：

- 最近若干轮原文，处理即时指代；
- 旧轮次的滚动摘要，保留任务和讨论方向；
- 带文档、页码出处的结构化事实，保留确认过的数字。

检索到的整页正文不进入长期记忆。具体数字只进入无歧义的事实条目，并强制携带来源；每次回答仍以本轮检索内容为最高优先级。

每轮开始时，还会先把用户的追问改写成可独立检索的问题，并判断是否需要重新查文档。例如“刚才那个数字”需要结合历史，而“把它改成表格”可能根本不需要再检索。

这说明 RAG 的边界不应该画在“向量库”上。一个可用的系统至少包含：

```text
查询重写
  → 权限 / 时间 / 文档范围过滤
  → 多路召回
  → 融合与精排
  → 证据选择
  → 上下文预算
  → 带引用回答
  → 事后事实与引用校验
```

把这些东西全压给一个“检索增强生成”的 Prompt，系统当然会显得很蠢。

## 6. 没有分阶段评测，RAG 就会变成玄学调参

最消耗人的阶段，其实不是写检索代码，而是判断一次改动到底有没有用。

只看最终答案是否正确，信息太少。答案错了，可能是：

- 文档选择漏了；
- 正确页面没召回；
- 页面召回了但没进 top-k；
- 页面进了上下文但正文截断；
- 数字正确但期间或口径说错；
- 回答模型无视了证据；
- 引用页码存在，但内容不支持结论。

这些问题的修复方式完全不同。

所以评测至少要分成几个层次：

- **文档召回率**：需要的文档是否在候选里；
- **页面召回率**：需要的页面是否在候选里；
- **页面精排质量**：正确页面是否进入最终预算；
- **证据完整度**：回答所需的所有页面是否齐全；
- **引用正确率**：每个关键结论是否真的有对应来源；
- **答案正确率**：数值、期间、单位和口径是否正确。

评测集也不能只放简单事实题。至少要覆盖：

- 无年份的定性问题；
- 需要跨年比较的问题；
- 图表与正文混合的问题；
- 重述前后口径不同的问题；
- 答案分散在多个页面的问题；
- 文档里根本没有答案的问题；
- 用户问题本身带有错误前提的问题。

如果正确页面在一开始就没有被召回，继续优化回答 Prompt 基本是在浪费模型调用。先定位检索漏斗在哪一层漏水，比反复修改“请你更准确地回答”有用得多。

## 7. 那 RAG 到底适合什么？

我现在更愿意把 RAG 定义成：

> **一种从外部语料中定位证据、组织上下文，并让模型在有出处约束下回答的工程方法。**

它不是一个向量数据库，也不是一个固定模板。

它很适合：

- 答案存在于私有文档中；
- 事实会更新，不能全部固化进模型参数；
- 用户需要看到出处；
- 语料规模大到无法整篇放进上下文；
- 问题可以通过检索若干证据后回答。

它不适合被拿来假装解决：

- PDF 解析本身就是错的；
- 文档没有可靠结构；
- 查询需要精确 SQL 或聚合计算；
- 答案依赖完整知识体系而不是局部证据；
- 没有评测集，只能靠几个 demo 判断效果；
- 权限、版本、删除和索引更新没有设计。

最常见的失败不是“RAG 不会推理”，而是我们把一堆本来应该由工程解决的问题，包装成了一次向量相似度搜索。

---

## 8. 最后

做完这两个项目之后，我对 RAG 的看法反而更积极了一点。

“RAG sucks”成立，是因为很多 RAG 系统真的只做了三件事：切块、embedding、拼接 Prompt。它们既没有表示文档，也没有表示问题，更没有表示什么叫做“证据充分”。

但一旦把文档结构、元数据、时间意图、多路召回、层级精排、上下文预算和评测拆开处理，它就不再是一个碰运气的黑盒。

我的几个结论是：

1. **先决定检索单元，再选向量模型。** 错的分块方式，换更大的 embedding 也救不了。
2. **不要让粗粒度层级做硬剪枝。** 文档层负责收窄范围，页级负责精确判断。
3. **相似度只能产生候选，不能证明答案。** 候选之后还需要融合、精排和证据校验。
4. **索引不是正文。** 摘要负责找，正文负责答，二者应该有不同的大小和生命周期。
5. **先把评测拆到检索层。** 页面都没召回时，不要怪回答模型。

RAG 真正“烂”的地方，不是它不能把相关文本找出来，而是我们经常期待它顺便完成文档理解、信息架构和证据审计。

这些工作不做，RAG 确实很烂。

做了之后，它只是一个正常工程系统。
